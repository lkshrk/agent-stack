# Sessions, feedback, blockers and refresh reports

Use the existing notes/dataset and stable IDs. These are small additions to the achievement workflow, not a new task service or a mandatory journal.

Preserve the chosen Obsidian or plain Markdown destination. For a one-off Markdown session, keep one file with relative standard links, normal checkboxes and end-of-file supporting details; use Plans and an existing index only when part of the established collection. No plugins, wiki links, dashboard or empty folder tree are required.

## Plan a playable session

Reuse the chosen character, starting location, available time, helper availability and category scope. Ask only for missing inputs that materially affect feasibility. Select researched actions that fit the conservative total-session budget, including shared travel and sequential waits; show conditional alternatives separately.

Begin with a short start card: executor, known or assumed starting point, required verified unlocks/travel options, optional time budget and source date. An assumed start is not a claim about the player's current location; include the access leg separately. Without a supplied budget, use a natural quest-hub or zone section as the chunk and report its estimated duration. Order unlocks before dependent actions, weaving nearby quest objectives, fixed treasures, exploration and compatible farms into one route so category lists do not cause repeated travel.

Separate **Before the tour — check once** from **Tour — start here**, with optional grinds and waiting work outside the core. Name the first actual task in the opening. Move full budget tables and account/source discussion below the route. Explain unfamiliar quest branches at their first affected stage under a labeled prerequisite check; mark their actions consistently and say which independent step to take if locked. Follow the [note structure](data-and-output.md#note-structure) rather than mixing prerequisites, background and checkboxes at the same heading level.

A session checklist references canonical achievements but tracks **actions**: buy/use an item, finish a run, earn a measured amount of reputation, check an unlock, or attempt a mechanic. An action can advance several achievements, and an achievement can span several sessions. Completing a session action does not automatically check an achievement or award AP.

Show **Repeatability / limits** before each distinct method using the [repeatability contract](data-and-output.md#repeatability-and-limits). Separate a repeatable activity from its rep/loot/criteria eligibility, state known quotas/reset scope/standing ceilings and what happens after the limit, and mark unverified limits unknown. A shared label may cover identical tasks. Session budgets must stop at the first credit/resource/availability limit rather than assuming more repeats produce more rewards; fixed one-time work can still be doable now.

Give each action a descriptive verb-and-target title, linked achievements, executor, method/route, planned duration range, expected progress, prerequisites, and stopping/skip condition. Keep stable IDs in supporting records or existing anchors; do not expose alphanumeric route codes in titles, directions or TomTom labels. Separate core work from optional additions and make dependencies explicit. Keep shared rewards unique per account. Use native task views for achievement completion; distinct action checkboxes must not match the achievement-completion parser or enter dashboard AP totals.

For a step that could fail in play, give **If blocked: continue with [descriptive action name/link]**, the observable trigger and the smallest useful check before leaving. The destination must be reachable without the blocked step; skip its dependent actions too and recompute remaining time/rewards. If no independent work remains, end at a clear stopping point and move the blocker to the conditional or waiting section. Never turn a fallback into rare camping, repeated availability checks or an unbounded troubleshooting task.

Number task titles and their TomTom labels with the same simple step numbers, restarting at 1 per self-contained section. Entrance and destination pins for one task share its number and have descriptive suffixes, ordered as visited. Do not independently number the pins or leave checklist tasks unnumbered. Plain sequence numbers are not opaque internal route codes.

End each chunk at a sensible turn-in, quest hub or zone boundary. State the progress to verify, where to stop, the next action by name and the character/location needed to resume. On refresh or restyling, preserve checkmarks and point the opening at the next unchecked action. Do not treat a finished chunk as an automatically completed achievement.

Keep a session in one note under `Plans/` or a section of the existing plan, with links to detailed instructions. Add a new note only when the itinerary/log would otherwise clutter the everyday checklist; register it on `Start Here.md` with purpose and source date. Supporting audits and checks stay under `_System/`, linked in a collapsed bottom callout. Record unresolved rotations, helper recruitment or unknown effort as conditional; do not silently squeeze them into the budget.

## Trial a new route

For a large new plan, make the first chunk one representative zone or quest hub with verified access and useful immediately executable work. Apply the same source checks to every published chunk; the trial is gameplay calibration, not permission to publish guessed later steps. Keep the remaining requested scope and coverage visible, and deliver a full plan when requested without waiting for the user to play. Mark unplayed routes as researched but not gameplay-validated; a small request needs no extra trial phase.

After the trial, accept an optional short report: where the player stopped, roughly how long it took and what was confusing or blocked. Check whether instructions were executable, nearby activities were combined sensibly, waiting leaked into the route and the planning range matched the actual starting conditions. Revise affected instructions, fallback paths and comparable timing estimates using the feedback rules below. Do not require per-task timers or claim that template tests validate gameplay quality.

## Learn from actual play

Accept a short report such as "planned 30 minutes, took 65; 20 minutes finding the entrance; finished two of four criteria." Record:

- Action/route ID, date, character and starting conditions.
- Original planned range, observed total duration, and known active/travel/wait components.
- Progress before/after, completed/partial/abandoned outcome, gold/currency spent when supplied.
- Delay or failure reason and evidence/source (user report versus measured timer).

Keep estimates and actuals separate. Do not invent detailed time components from one total. For partial sessions, report the achieved progress and remaining uncertainty rather than treating the session duration as full completion time. Reprice comparable activities only: first attempts differ from repeat runs, and routes differ by start/access. Do not multiply every estimate by one bad run's ratio or extrapolate RNG attempts into guaranteed completion.

Use overruns to improve the relevant step: navigation instructions, missing prerequisites, helper coordination, retry allowance, or throughput. Update future planning estimates and explain the change; preserve the original value in the feedback record. Logging remains optional, and a missing log must not block completion updates.

## Turn blockers into next actions

For each blocker retain the affected achievement/action and character, the exact requirement, what is observed, what is unknown/unmet, and the smallest check or unlock that resolves it.

Examples:

- **Vendor availability unknown:** check the specified vendor at the linked location before travelling further; clear when stock/quote is observed.
- **Reputation below threshold:** show required and observed standing for each eligible candidate; provide the acquisition path and remaining amount.
- **Quest access unknown:** identify the prerequisite quest/phase and the source needed to verify it; do not prescribe the entire quest chain without checking existing progress.
- **Helpers needed:** specify verified player count/roles and availability; an unverified minimum is a separate research blocker.
- **Inventory unknown:** identify which storage was not scanned and whether that uncertainty affects purchasing quantity or merely confidence.

Include direct Wowhead links and verified TomTom commands where relevant. Distinguish a known unmet requirement from missing data and unsupported source coverage. Clearing a blocker requires the corresponding evidence, not just removal of its tag.

## Report each refresh

Compare like-for-like account, character and observation scopes. A newly downloaded response with old scan times is not fresh game state. Compute a candidate diff before applying an authorized update; unresolved contradictions remain explicit instead of overwriting user intent.

Report previous/new observation dates and link changed IDs grouped as:

- Newly game-confirmed completion, distinguishing previously checked versus unchecked tasks.
- Newly discovered incomplete work and previously known work that became eligible.
- Changed criteria, resource quantities, eligible executors, blockers or planning estimates.
- Manual/source conflicts and unavailable/stale fields.
- Deliberate deferrals preserved and records left untouched outside the selected scope.

Show significant AP/shopping/time impacts with deduplicated totals; omit noisy unchanged fields. A user checkmark is not a source discrepancy to erase. A missing API ID is not completion, and a new catalog ID is not necessarily an incomplete obtainable achievement.

Separate coverage levels: fetching current definitions is not verifying completion methods. Report both counts. Keep unreviewed historical estimates out of timed recommendations. Positive-only criterion feeds do not establish zero for absent entries; opaque website character IDs must not be guessed from class or level, and character-scoped criteria must not be combined across alts.

Check faction counterparts before reconciling catalog AP. If only a newly computed total is available, retain the last independently reported account total with its date and label the new calculation separately. For collection purchases, absent current stock is not evidence that an item never earned first-acquisition credit. Test one purchase before a large basket; verify currency units, vendor unlocks and cumulative-tier overlap. Calibrate crafting credit per cast and hand-in credit per batch before bulk buying.

Use the existing setup/update note for this report. Apply only the requested refresh scope, then verify reported counts against the resulting data and live views. Repeating the same import must not duplicate tasks, reset action progress, remove annotations, or re-enable intentionally deferred work.
