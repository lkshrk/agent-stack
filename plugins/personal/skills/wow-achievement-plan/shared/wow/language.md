# Request, client and source languages

Accept non-English and mixed-language requests, including localized game names and player-reported state. Route by meaning; English examples in a skill are not a keyword whitelist. Follow an explicit reply-language choice, then the established preference, otherwise the current request's language. Keep the game-client language separate: reuse a known client locale or the user's stated game-name preference; do not infer it from account region, realm or character name. Missing locale alone does not block a general answer.

Use the reply language for explanations, headings, checklist actions and waypoint descriptions. Use verified names from the client's language for game entities when known; an English reply can still need German item names. If a localized name is unavailable, retain the verified source name and direct entity link, explaining the fallback once rather than inventing an official translation. Resolve localized or ambiguous names to the correct game/version and stable entity ID using source evidence; ask only when unresolved ambiguity changes the answer. Prefer a verified localized Wowhead page when available; a canonical English ID link remains valid when the localized page is unavailable or unverified.

Treat localized player-state statements as user-reported evidence with their original wording and scope. Map their meaning to existing internal states only when clear; distinguish completed, incomplete and unknown, including negation. A translated statement or screenshot does not become an API-confirmed observation. Preserve the existing refresh requirements for personalized recommendations.

Join observations by account-scoped GUIDs and entity IDs, never by translated display names. Preserve Unicode character/realm names, raw values, source language when known, timestamps and provenance. Do not translate, transliterate or strip accents from identities. Region, API locale and provider identifiers are separate fields: resolve a provider's canonical class/spec/realm identifiers before invoking its tools, rather than passing translated display labels as identifiers. Missing or unsupported localized fields remain unknown/unsupported; do not assume a translated export has the same schema or erase earlier observations.

Translate display text, not JSON keys, enum values (such as `incomplete`, `unknown`, `ready`), category tags, stable record/block IDs, existing paths, API parameters or encoded talent strings. Retain the established task anchors and manual progress when changing a guide's language. Keep technical import/coverage reports intact when scripts consume them; summarize their findings in the reply language. Bundled Obsidian controls and diagnostic reports currently have English labels; localized task content works without a translated UI. Explain that limitation when relevant, without promising a fully localized renderer.

TomTom syntax stays `/way #MapID X Y Label`: use the verified numeric UI map ID, ASCII digits, decimal points and space-separated coordinates in fenced `text` blocks. Only the human-readable label is localized. Do not translate slash commands, switch to a localized zone-name selector or introduce decimal commas. Apply the same rule to rendered copy buttons and retained routes.

When saving or refreshing an existing setup/plan, retain the reply and client-language preferences alongside its other preferences; source locale belongs to source provenance when known. Do not create a separate language database or rewrite a whole account just because the conversation language changed. For a duo, retain each player's client-language preference and choose the shared tour's reply language from the request; include both verified entity names only where they help the pair identify the same target.
