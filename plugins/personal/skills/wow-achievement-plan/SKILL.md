# WoW Achievement Plan

Complete the user's selected goal. For a native achievement plan, optimize obtainable account achievement points within that scope and shared travel/setup; other progression goals follow the branch below. Produce the researched checklist, not a proposal to research it.

## Resolve game and goal type first

Follow [game context and supported capabilities](shared/wow/game-context.md), asking the version when unclear, and reuse [versioned sources](shared/wow/versioned-sources.md). For a quest, reputation, profession, item, leveling or Legacy goal without native achievement credit, follow [progression goals](shared/wow/progression-goals.md) instead of the achievement/AP-specific flow below. Deliver that Markdown plan without inventing achievement IDs, AP or missing-scan requirements. Existing source freshness, repeatability, timing and preservation rules still apply.

## Required data refresh before planning
Before selecting, ranking, routing or estimating personalized work, refresh the local account data; if the refresh fails or freshness cannot be established, stop and ask the user. Follow [shared/wow/data-refresh.md](shared/wow/data-refresh.md) exactly.

## Choose the output
Default to plain Markdown unless the user chose Obsidian or an established workflow exists. Follow [shared/wow/output-format.md](shared/wow/output-format.md).

## Maintain generated artifacts
Update existing guides in place and clean up only what you generated. Follow [shared/wow/generated-artifacts.md](shared/wow/generated-artifacts.md).

## Resolve the target

For Obsidian, place playable plans, session routes and long-term project guides in `WoW/Plans/` (or the selected root). Register every generated guide on `Start Here.md` with its purpose, source date and current/historical status; link the dashboard and everyday lists there too. Store supporting datasets in `_System/Data`, persistent canonical achievement progress in `_System/Task Records`, research/coverage in `_System/Research`, verification reports in `_System/Validation`, and superseded generated output in `_System/Archive`. Keep temporary agent work outside the vault, preserve personal notes, and do not archive a still-useful guide merely because it is old. Put technical/source links in a collapsed callout at the end of the guide. For the portable dashboard, follow its actual bundle paths; progress records are never disposable working data.

Use the current request or an existing plan for character, realm, region, game version, and output folder. Ask for missing identity; never inherit a character or account total from this skill's originating session. For every request, follow [request, client and source languages](shared/wow/language.md).

Establish the route's starting conditions from current evidence or the user's last update: executing character, current location, unlocked zones/quest phases and usable travel options. Old location data is not a live position. If location is unavailable, state a practical route-start hub and estimate access separately; do not assume the player is already there. Session length is optional: use it when supplied, otherwise chunk at natural quest-hub/zone boundaries rather than imposing a time limit. Ask only when missing context changes feasibility; keep unknown access out of the executable baseline.

Inspect existing WoW notes before choosing paths or syntax. Only for Obsidian output, inspect installed features. Prefer the existing `WoW/` folder and update matching notes rather than creating duplicates. For Obsidian, use an available connector or an accessible local vault; for plain Markdown, write directly to the selected folder. Discover the connector's actual tools and schemas; do not assume an endpoint or request credentials in chat. If vault access is unavailable, prepare the complete artifacts locally and report where they are, without claiming publication.

Carry forward established preferences. Within the selected categories, consider AH/vendor purchases, professions and switching, collections, world content, instances, PvP, grinds, and time gates rather than silently excluding a content type. Unknown gold budgets or alt capabilities make affected recommendations conditional; they do not block research of the rest.

## Choose search scope and operation

Offer **Create a plan** or **Update an existing list** and the following multi-select categories. Accept names, numbers, any combination, or **all**. Reuse explicit choices in the request; on update reuse stored scope unless the user changes it. When no choice exists, ask one compact scope question while inspecting available data, before beginning broad category research. Record the selection with the plan.

| Category | Required result |
| --- | --- |
| 1. Quick wins | Short, practical completions with low total setup/travel cost; expose the chosen time budget rather than treating a brief final click as a quick win. |
| 2. Buyable | Achievements advanced/completed through purchases, with a concrete itemized buy list, quantities, prices, vendors/AH source, prerequisites, and eligible buyer/user characters. |
| 3. Grindable | Work that can be advanced now, including finite quest chains, exploration and treasure routes as well as repeatable farms; give ordered remaining steps or a repeatable loop, realistic effort, session chunks and stopping condition. |
| 4. Long-term projects | Time-gated or multi-stage objectives with an ordered path: unlocks, reputation/currency requirements, recurring actions, milestones, and active versus calendar estimates. |
| 5. Short tasks needing help | Brief completions once helpers are ready; specify minimum total players and additional helpers, required roles/actions, prerequisites and ready-group duration separately from recruitment/coordination time. |

Research and publish the union of selected categories; do not force quick wins into a long-term-only request. Categories can overlap: a purchase may also be a quick win or one step of a long-term project. Keep one canonical achievement task, show it in each applicable selected view, and deduplicate AP and shopping quantities across those views. Research prerequisites outside the selection only as dependencies, not as a silently expanded recommendation pool. Detailed deliverables are in [the category contract](references/data-and-output.md#category-deliverables).

For category 5, use the user's short-session threshold, or state a default of 30 minutes once the group is ready. Verify that extra players are actually required by the current mechanics, rather than merely helpful. Include mandatory setup/travel in that ready-group estimate; show recruitment separately and include it in the full planning duration when known. Unknown recruitment time means conditional session fit, not instant availability. Category 5 alone does not imply a task qualifies as an immediately executable quick win. A stored `all` selection includes all five categories; an explicitly stored subset stays unchanged on update.

### Focused goal or scope requests

Accept natural-language requests such as "create a plan/todo list for XYZ" or "non-time-gated grindable BfA achievements" as sufficient scope. Extract the target expansion, zones, named achievements/metas, activity types and exclusions; do not force another category-selection question. Persist these constraints alongside category choices and preserve them on refresh. An expansion or zone limits the objectives; necessary access/travel dependencies can lie elsewhere and must be labeled as setup.

For the BfA example, screen the account's remaining BfA achievements across quest/story chains, exploration, treasures and any other activities meeting the request. "Grindable" includes finite one-time work, not only repeatable kills or currency loops. Do not restrict the search to high AP/minute recommendations or a handful of famous achievements. Do not infer solo-only, a short-session limit or no purchases unless requested; show actual character, group and cost requirements.

Prioritize **"can just do it now"** over nominal absence of a daily cooldown. The main route must offer productive actions the player can start and keep progressing without camping, checking availability or waiting for other people. Include accessible quest chains, fixed treasures, exploration and farms with continuously available attempts. Long effort is allowed; long idle waits are not. Do not route through rare-spawn camps, hour-long respawns, dailies, rotations or events just because their final interaction is brief. An immediately repeatable random drop can qualify with an attempt budget and uncertain completion; a random drop behind rare-spawn waits cannot. Required helpers must already be available or that action stays conditional.

Check the whole remaining completion path: prerequisites, quest unlocks, reputation/currency acquisition, reward eligibility and difficulty-specific reset rules. Already-satisfied gates do not block the remaining path. When an achievement also requires waiting/gated criteria, put its useful ungated actions in the main route as **partial progress only**, and put the remaining requirements in a separate **Waiting / gated requirements** section linked to the same canonical achievement. Show the exact requirement, why it cannot just be done, cadence/respawn uncertainty, smallest availability check and what remains afterward. Keep those steps out of main-route timings and completion/AP forecasts; do not claim the achievement or a dependent meta will finish. This section is for requirements of the requested goals, not an unsolicited catalogue of dailies. Keep unknown availability/access outside the executable route with a concrete verification step. If the user explicitly requests only fully completable achievements, omit partial-progress actions too and explain the exclusions.

Deliver an ordered action checklist, not just achievement names or separate category lists: access/unlock quests first, then zone routes combining quest objectives, nearby treasures, exploration and compatible farms. State which actions unlock later steps, which can be combined and where to resume. Each step gives the remaining objective/quantity, eligible executor, location, exact Wowhead links, TomTom commands where applicable, conservative planning duration and a completion/stop check. Reference canonical achievement IDs; action checkboxes track route progress without independently awarding achievement completion or AP. Split long routes into resumable chunks without inventing a daily cadence. Use the focused-plan layout in [the output contract](references/data-and-output.md#note-structure).

Use the [playable-session contract](references/session-and-refresh.md#plan-a-playable-session) for start/resume details and explicit fallback steps. For a new large route, make one representative zone or quest hub the first playable trial and use optional player feedback to calibrate later chunks. Keep the full requested scope visible and finish a requested full plan; do not wait for gameplay feedback or claim unplayed routes are validated.

## Acquire and validate before ranking

Reuse the dated source/identity map from `wow-account-setup` when available. For essential source or named-character gaps, invoke that skill if installed; do not restart onboarding when coverage already suffices. Independently, check available website data, exports and exact GUID-to-name records in roster addons before requesting repeat scans. Public redaction is not missing game data, and an old snapshot is not current state. Keep unresolved identities conditional rather than guessing.

Before using old snapshots/public caches or asking for an upload, inspect the private setup record and relevant environment documentation/tool registry for the configured local/game-data reader and its transport. Use that documented read-only access rather than assuming an SMB mount; an SFTP-backed adapter or Coder `wow-sv` reader may already exist. User-designated current local data must be inspected, or its specific access failure reported. Read complete exports, not truncated CLI previews, and verify source/export file modifications plus per-field scan clocks; retrieval time does not refresh cached observations. Public account APIs may supply explicit remaining criteria/account AP missing from positive-only addon data, with separate scope and dates. Keep the reusable access-method reference in the private setup note, never machine-specific hosts/keys in portable skills or shared guides.

1. Obtain current machine-readable character/account data from Blizzard, Simple Armory, or another verifiable source. Inspect current network/API behavior when necessary. Record source, retrieval time, region, and version; never bake live endpoints or patch assumptions into the plan.
2. Join achievement definitions to observed player state by achievement ID. Distinguish **completed**, **incomplete**, **unknown**, and **unobtainable**. An ID absent from the profile is unknown, not incomplete. Separate account completion from character-specific criteria, professions, recipes, currencies, reputation, and access.
3. Reconcile completed point totals with the profile/account total using the source's counting semantics. Sample completed and incomplete entries and partial criteria. Report mismatches and coverage limits; restrict recommendations to supported incomplete records rather than forcing the totals to agree.
4. Exclude completed, unobtainable, zero-point, and Feat of Strength entries from AP forecasts. Check whether legacy entries still award obtainable AP instead of excluding by label alone.
5. Persist a normalized dataset and coverage ledger using [the data contract](references/data-and-output.md). Screen the known incomplete pool for selected-category membership, then research that scope comprehensively. Distinguish in-scope, out-of-scope, unclassified, individually researched, conditional, and deferred records; do not claim all were researched because they were enumerated. A restricted search must not erase existing tasks in other categories.

If the data is inaccessible or does not establish incomplete state, stop the personalized ranking branch and request a usable export or access. A generic list is not a substitute. Preserve an existing valid plan on refresh failure.

## Research effort and feasibility

**Repeatability and limits are core output, not a footnote.** For each method, verify and display a compact **Repeatability / limits** line before its todo steps: one-time credit, repeatable progress now, daily/weekly cap, cooldown/lockout, rotation/event/spawn dependency, or unverified; add material, access, group/queue and RNG constraints as applicable. Distinguish activity repetition from the requested rep/loot/currency/achievement credit. Include reward/reset scope, standing ceilings and reduced/zero rewards after a cap when relevant. “Grindable” must mean the desired progress can continue now, not merely that the player can repeat an action. One-time fixed quests/treasures can still be valid no-wait tasks. Unknown limits do not qualify as unlimited; keep affected recommendations conditional until verified. Use [the repeatability contract](references/data-and-output.md#repeatability-and-limits) in guides, session lists and refreshes.

Research promising candidates against the current game version. Start with exact Wowhead achievement pages and dated comments, then Warcraft Wiki and current reputable guides. Cross-check community reports for uncertain mechanics. Record links and dates for conclusions; old comments alone do not establish current soloability or prices.

For each recommendation establish remaining criteria, difficulty, players needed, lockout interactions, prerequisite quests/phasing, current soloability, RNG, and travel access. Verify gold shortcuts, profession/recipe availability, collection thresholds, and Warband behavior. Do not infer effort solely from an achievement description or assume a counter on one character describes every alt.

Use current regional prices where practical, otherwise label gold estimates unverified. Mark unresolved prerequisites or mechanics `⚠️ VERIFY` and keep their reward out of the executable baseline.

Make each blocker actionable: state the exact missing fact, affected character/action, how to check or unlock it, and what evidence would clear it. Distinguish unknown data from a known unmet requirement. A generic `VERIFY` label alone is insufficient; use the [session and refresh contract](references/session-and-refresh.md) for blocker records and play feedback.

### Show which characters can do the task

Build or refresh a roster from available account data, user-provided exports and known alts; store region/realm/name, observation date, and verified capabilities. Public data for one character is not a complete roster. Where needed, request missing roster or capability data while continuing verified work.

For every restricted task, display **Eligible now: character names**, **Eligible after setup: names + exact missing requirements**, and **Unknown: names/capabilities needing verification** as applicable. If none qualify, say so and give the unlock path. Show the actual threshold and observed value (reputation, profession expansion/skill, known recipe, level, faction, currency, quest/phasing or access), not merely a generic `requires profession` warning. Evaluate all requirements on the same executing character; do not combine one alt's reputation with another's profession unless the mechanic explicitly permits it.

Choose a recommended character and explain the advantage, while showing the other verified options. Include switching, travel, unlock and profession-change costs in that character's estimate. Do not assume character-bound currencies, recipes or reputation are shared because achievement completion is account-wide. For purchases, distinguish who can buy, who can learn/use, and whether an item can be transferred. Unknown eligibility stays conditional; never invent alts or claim the roster is exhaustive when it is not.

### Estimate the whole job, not the final interaction

The originating plan substantially underestimated most durations. Treat its timing figures as uncalibrated, not evidence. Estimate for this player doing the remaining work, including a first attempt, rather than an expert speedrun with every prerequisite ready.

- Break time into understanding instructions, prerequisite work, shopping/setup, travel/loading, execution, queues/waits, likely retries, and completion verification. Show what was included and what was already completed or assumed available.
- Keep active, travel/setup, unattended/waiting, and calendar gates separate. Also show **session duration**: wall-clock time from the stated starting point to completion. Count sequential waits and unattended crafting if they delay completion; subtract overlap only when the proposed route actually uses that time for another task. Reset days stay separate from playable session minutes.
- Give a plausible range and a conservative **planning duration**, normally the upper end, with an evidence source, date, assumptions and confidence. Do not imply a guaranteed maximum or statistical percentile without supporting data. A mechanic with unbounded RNG gets a bounded attempt budget and uncertain completion, not a promise of AP within that budget.
- Prefer this player's measured comparable runs, then current ordinary-player reports or observed timings, then a researched step-by-step estimate. Add explicit allowance for evidenced navigation/learning/retry costs; do not invent precision or hide uncertainty behind an arbitrary global multiplier.
- On refresh, retain estimated versus actual times and why they differed. Recalibrate comparable activities when the user reports an overrun, preserving different scopes (first-time versus repeat runs, different starting locations). If no defensible estimate exists, mark it unknown and keep it out of time-bounded recommendations.

Recompute rankings, effort tiers, and route budgets from these estimates. Show active effort as a secondary breakdown; use planning session duration for the practical quick-win ordering so a two-minute interaction behind 40 minutes of setup cannot rank as a two-minute task.

When the user reports actual play time, record it against the planned action and starting conditions, with partial progress and delay reasons. Keep the old estimate for comparison; use the observation to reprice comparable work rather than silently rewriting history. Follow [session feedback](references/session-and-refresh.md) without imposing a logging step after every task.

## Rank actions and routes

Separate rotating WQs, delve stories, seasonal events, offered-daily variants and personal reset/timer checks into a condensed availability table: **Achievement (Wowhead) | Expansion, continent / area | TomTom command | What / who | Check if up**. Sort by expansion release order, then region/area. Exclude these from normal execution recommendations until the required availability is verified. Keep canonical tasks and manual status intact; the table is another view, not duplicate tasks. A normal instance lockout, generic grind or RNG drop alone does not prove a rotating activity.

Give a validated in-game availability command where supported. Label exact WQ visibility queries, map inspection, entrance-panel story reads and nearby NPC targeting distinctly. Never use a quest-completed flag as proof the quest is currently offered. Negative/missing task data can mean completed, locked, phased or unloaded; do not label it globally down. Opening a map is a manual check, not automatic detection. If no reliable command or waypoint exists, state that and the smallest manual check. Commands are displayed for the user, never run automatically; record API source, date and in-game test status.

- Report base AP and marginal effective AP. Effective AP includes only additional achievements whose remaining requirements this action or bundle actually completes. Award each ID once, including shared and cascading metas. A partly progressed meta is not earned AP.
- Show `effective AP / active minutes` as a hands-on efficiency measure, and use `unique effective AP / planning session minutes` for practical ordering and routes. The latter includes required setup, travel and sequential waits. Unknown time is not zero; do not report infinite efficiency. Show calendar constraints separately.
- Explain adjustments for near-completion (especially ≥80%), reliable gold shortcuts, passive progress, shared setup, travel, RNG, group/PvP dependency, lockouts, phasing, prerequisites, profession switching, and expense. Prefer transparent comparisons over invented numerical weights; avoid counting an advantage twice if it already reduced estimated time.
- Form city-shopping, profession, instance, zone, and continent bundles. Recompute unique rewards and shared travel for the bundle; do not add independently estimated effective rewards together. Show which actions unlock another reward.
- Route geographically using verified portals, hearthstones, toys, transport, class abilities, and access on the executing character. Do not assume faction, unlocked hubs, or teleport ownership. Independent mini-tours can beat one chronological expansion tour.
- Research the selected categories comprehensively, including structured grind and long-term paths rather than only high-efficiency candidates. Retain the rest with scope/deferral reasons. Do not impose an arbitrary top-10 limit. Larger scopes may need resumable batches; state incomplete coverage explicitly.

## Publish and refresh

Make the playable structure unmistakable: **Before the tour — check once**, then **Tour — start here**, followed by separate optional grinds and waiting work. Name the next unchecked action in the opening; put full estimates and source discussion after the tour. Use descriptive action names in tasks, skip/resume directions and TomTom labels; keep internal route IDs out of reader-facing text. Explain unfamiliar quest branches at their first relevant stage with labeled prerequisite checks and affected actions. Use [the note structure](references/data-and-output.md#note-structure) so the reader never has to infer whether a paragraph is background, a check or the next task.

For a requested "today" or "next session" checklist, select a bounded set of actions from existing researched tasks using character, time budget and available helpers. Link to canonical achievement records, distinguish action progress from achievement completion, and include a stopping condition. Use [the session checklist contract](references/session-and-refresh.md); do not create a second independent set of achievement checkboxes.

Use the note structure and reporting fields in [the output contract](references/data-and-output.md). For focused requests, lead with the ordered goal/zone checklist; category filters remain secondary views. Otherwise, when quick wins are selected, begin the note body with `⚡ Quick Win TODO List`; or begin with the first selected category. Include optimized mini-tours where useful. Every named achievement, including metas, gets its direct Wowhead achievement-ID link in every deliverable: todo, dashboard and report. Link actionable NPCs, items and quests to their exact Wowhead pages too. A slug is optional; generic search links or an internal note link alone do not replace Wowhead. If an entity ID is unresolved, mark the link unresolved instead of inventing it.

### Copyable navigation

Number the checklist and waypoints together. Use simple numbered task titles (`1. Collect ...`, `2. Complete ...`) within each self-contained route section, and put the **same task number** in its TomTom labels. Entrance, approach and destination pins for one task share that number, with clear descriptive suffixes and travel order in the block; do not independently number pins and make them diverge from the checklist. Tasks without travel need no invented pin. Preserve checked states and keep optional sections distinct. These useful step numbers are not opaque internal IDs and must survive naming simplification.

Every displayed navigation coordinate MUST be a complete TomTom command inside a fenced `text` code block: `/way #MapID X Y Label`, with a verified numeric UI map ID replacing MapID and a label following the language guidance. Never use a region/zone name or omit the map selector. Use spaces between X and Y, never commas. One command per line; no quotation marks, Markdown styling, bullets, blockquote prefixes, or explanatory prose inside the copy block. Do not display bare coordinate pairs anywhere, even when a correct command also appears elsewhere. This applies to task bodies, tables, summaries, shopping, historical/completed entries, Obsidian and plain Markdown. Tables should link to the nearby command block instead of embedding coordinates. Keep blocks adjacent to the relevant task and include an ordered block for each mini-tour.

Before publishing or finishing a refresh, scan every affected note including canonical source notes and retained history: confirm balanced fences, every waypoint inside a `text` block, a verified zone/map, two numeric coordinates in the 0–100 range, and a label following the language guidance. Read back the saved files. Do not pass malformed legacy coordinates through unchanged merely because task text is preserved; normalize their presentation while retaining task status and annotations. If the map or location is unresolved, replace the coordinate display with an explicit waypoint-unavailable note and sourced access guidance rather than guessing.

Use `/way #MapID X Y Label`, replacing every token with verified values. Verify the exact map/floor, game version and required timeline; city and parent-zone maps may use different coordinate systems. A numeric map ID does not itself establish quest phasing or switch timelines, so retain those access requirements. Distinguish entrances from interior objectives. If the map ID or location cannot be verified, mark `⚠️ VERIFY — TomTom waypoint unavailable` and give sourced access instructions rather than falling back to a zone name or guessing. Mention that TomTom is required; its `/ttpaste` window accepts multiple commands. See [TomTom's command documentation](https://www.curseforge.com/wow/addons/tomtom).

Use standard Markdown checkboxes; preserve existing tags/frontmatter where supported. Apply the per-achievement [filter metadata contract](references/data-and-output.md#filter-metadata) for category, effort, player requirements and relevant restrictions. Store metadata on each canonical task/record, not solely in note-wide frontmatter. Give each achievement one canonical task keyed by achievement ID; other sections link to it or query it. Meta bonuses should be linked projections rather than duplicate actionable checkboxes. This makes dashboard totals and future updates reliable.

Prefer stable source notes with live Todo/Backlog/Completed queries when the vault supports them. Completion cleanup then changes the view, not the task's file location. Keep checkbox editing native to the source task and preserve the distinction between imported game completion and manual checkmarks. Reuse an existing live-view layout on refresh instead of rebuilding physical completed-file archives.

Before writing, verify dataset scope, exclusions, prerequisites, effort evidence, unique meta rewards, routes, and links. Then write and read back the notes and data. Preserve user annotations and task status on refresh by ID. Treat checked tasks as manually reported completion, separate from source-confirmed completion; show conflicts instead of silently unchecking work or increasing confirmed account AP. Do not delete stale tasks or user notes merely because an API response is missing an ID.

### Update an existing list

Offer a full update (account refresh, completed cleanup, new candidates and revised remaining work) or accept any requested subset. A bare "update my list" means the full update within its stored category scope. An explicit cleanup-only request does not initiate new candidate research.

Read the existing dataset, canonical tasks, annotations, category selection, character roster and destination first. Fetch and validate fresh account/character state before treating it as a replacement snapshot. Compare by stable achievement ID and plan/account identity, not names or positions.

- **Refresh account data:** update source dates, confirmed AP, criteria, roster capabilities and coverage; recompute remaining quantities, eligibility, paths, prices/estimates where stale, and unique forecasts. Keep unavailable fields unknown and retain the last valid observation with its date; do not present old data as fresh.
- **Clean completed:** remove confirmed completions from active todo, shopping lists, routes and future work; retain a linked completed/history section with annotations, evidence and mappings. Manually completed tasks may be hidden from active views with their manual label intact; surface conflicts with fresh incomplete state. No permanent deletion is implied by cleanup.
- **Add new:** find newly available or newly eligible incomplete achievements within selected categories, including changed criteria/unlocks and new catalog entries. An absent/unknown profile entry is not proof it is new unfinished work. Deduplicate existing and archived IDs; do not recreate completed or user-deferred tasks as new.
- **Refresh views:** rebuild relevant category views, shopping allocations, recurring work, routes and dashboard from the reconciled dataset. Do not remove excluded-category history or user notes.

Report the prior/new snapshot dates and counts added, revised, moved to completed, manually complete, unresolved/conflicted and outside scope. If retrieval fails, keep the last valid list and report which update steps could not run instead of publishing an empty replacement.

Keep a compact refresh report with the concrete changed IDs and reasons, newly eligible work, meaningful criterion/resource changes and unresolved conflicts. Compute the diff before applying the authorized refresh and verify it afterward; this is evidence, not an extra approval gate. Preserve user annotations, deliberate deferrals and previous estimates/actuals. See [refresh reporting](references/session-and-refresh.md).

Deliver the requested checklist in the selected output mode. Add a dashboard only when requested or already part of the established layout. Use `wow-achievement-dashboard` when available; in plain Markdown, any requested dashboard/index is static and explicitly dated. The planner does not require that companion skill to be installed.

When using `wow-achievement-dashboard` for Obsidian, populate its bundled note templates and view-data schema with this researched plan. Reuse its tested renderer rather than inventing another dashboard implementation. Keep account-specific sources, eligibility, estimates and evidence in generated data/notes; none belong in the portable template assets.
