# images

Built from the repository root (`docker build -f images/<name>/Dockerfile .`) and published as `ghcr.io/lkshrk/agent-stack/<name>` by `.github/workflows/images.yml`.

| Image | Contents |
| --- | --- |
| `omnigent-host/` | Runner: Omnigent host, Claude Code, Codex, omp with the workstation's shared skills and MCP servers, the `runner` plugin and others, LSPs and toolchains, sandbox tooling (gitleaks, Playwright Chromium), agent home seeding, credential helpers and the `agent_stack_policies` package, which the runner resolves at session start |
| `omnigent-server/` | Omnigent server with `bundles/`, `config/omnigent/config.yaml` and the `agent_stack_policies` package baked in. A release build pins the runner image of the same release (see below) |
| `agent-tools/` | The Go programs from `cmd/` on distroless |
| `hermes/` | Hermes with its managed configuration from `config/hermes/`, git and the vault tooling |
| `hermes-webui/` | Hermes web UI; pins the same Hermes image as `hermes/` (checked in CI) |

Both Omnigent images install `policies/omnigent/agent_stack_policies` under `/opt/agent-stack/policies` and add it to the venv with a `.pth` file. CI runs the policy tests inside both images with `AGENT_STACK_IN_IMAGE=1`, in each Dockerfile's `test` stage (`docker buildx build --target test`); the default target is the published image without it.

## Runner pin in the server image

The bundles resolve `agent_stack_policies` handlers inside the runner, so a server image must never point at a runner older than its bundles. `images.yml` builds `omnigent-server` with `AGENT_STACK_VERSION` set to the release version (the leading `v` removed), and the Dockerfile rewrites `sandbox.kubernetes.image` in the baked config to `ghcr.io/lkshrk/agent-stack/omnigent-host:<version>`, the runner built in the same release run. The rewrite is a tag pin without a digest. PR and local builds leave the argument empty and keep the pin checked in to `config/omnigent/config.yaml`. CI builds the server once more with the argument set and checks the rewritten line.

## Server image deviations from upstream

- The web UI's sidebar owner check is patched (`omnigent-server/patch-web-ui.sh`) to also honour `permission_level >= 4`, so admins get Stop, Archive and Delete on sessions they don't own by name. The build fails unless exactly one file and one occurrence match, and the `test` stage asserts the result. The same helper drives the shared/mine split, so admins see every session as their own in the UI (no Shared section, owner shown as "You"). Assets are served with a one-year immutable cache under an unchanged file name, so browsers need their site data cleared once after the deploy.

## Runner sandbox tooling

The runner image carries generic tooling so a project can run its own checks inside the sandbox pod, which runs as uid `1000660000` (`sandbox`, home `/sandbox`):

- `gitleaks` (mise) for the `security-review` bundle; the Codex profile sets the `MISE_*` variables, because mise shims fail with "not a valid shim" when a session does not inherit them. `test/security-review-tools.sh` runs every CLI the bundle calls under the profile environment.
- Playwright Chromium and its OS libraries live under `PLAYWRIGHT_BROWSERS_PATH=/opt/ms-playwright`; `/opt/ms-playwright/.playwright-version` holds the Playwright version they belong to (`PLAYWRIGHT_VERSION` in the Dockerfile). A project's Playwright pin must match it: bump both together. The Omnigent v0.19.1 Kubernetes sandbox cannot add a browser sidecar, so the browsers ship in the runner.
- `node` is the base image's Node 22, and the agent CLIs are installed under `/usr/local`. mise `auto_install` is off: the sandbox user cannot write `/opt/mise`, so a project pinning a node that isn't installed falls back to Node 22 instead of breaking every node CLI.
- The runner flattens the upstream `omnigent-host` image into one layer after removing kiro-cli and the upstream's Claude Code and Codex (reinstalled at pinned versions), because files removed in a later layer still ship; `test/removed-clis.sh` fails if a base bump brings them back. A flattened image loses the upstream's `ENV`, so the Dockerfile repeats it: when bumping `OMNIGENT_HOST_IMAGE`, copy its `ENV` again; `test/upstream-env.sh` fails if one is missing or differs. It loses the rest of the upstream image config too (`User`, `Entrypoint`, `Labels`, `Healthcheck` and so on), so CI runs `ci/upstream-config.sh` before building the runner: it fails if the upstream sets any config field other than `Env`, beyond the reviewed `Cmd` and `WorkingDir` that the Dockerfile restores. `images.yml` pushes the runner with a fixed `SOURCE_DATE_EPOCH` and `rewrite-timestamp=true`, so a cold rebuild of the same base yields the same flattened layer digest. Each install step removes its own caches and `build/prune-native-platforms` drops non-linux-x64 prebuilds from the npm trees; `test/native-platforms.sh` checks that. Rust is installed with the `minimal` profile plus clippy, rustfmt and rust-src, without the offline docs.
- Agents never prompt. Claude Code's managed default mode is `bypassPermissions` (Polly's worker sets it too), and Codex runs with `approval_policy = "never"` and `sandbox_mode = "danger-full-access"`, since bubblewrap can't create namespaces in the runner pods. The gates are Omnigent's `PreToolUse` policies (which still run in every mode; `claude-launch.sh` checks the hooks fire), the per-agent GitHub tokens and the runner's post-run check. Every shell-running bundle also has the best-effort `no_process_secrets` policy.
- Claude Code: under `bypassPermissions` the managed `additionalDirectories` (`/home/omnigent/workspace`) and the `EnterWorktree`/`ExitWorktree` allow rules only matter for a session started in another mode; the managed `deny` rules still apply in every mode.
- Codex: `seed-agent-home` writes `~/.codex/config.toml` with `features.unified_exec = false`, because input sent to a running exec session through `write_stdin` never reaches the `PreToolUse` policy hook. It also installs the file profile `~/.codex/security-review.config.toml`, which a session selects with `terminal_launch_args: ["--profile", "security-review"]`. The profile sets `approval_policy = "never"`, a permission profile that reads only the session checkout, system dirs (`/usr`, `/etc`) and the tool dirs (`/opt/mise`, `/opt/venv`, `/opt/agent/bin`), writes only `/tmp`, reads exactly one file under `/agent-secrets` (`github/review`, the read-only review token) and nothing else there, cannot read the home directory or its dotfiles, drops secret env vars (`*_KEY`, `*_TOKEN`, `*_SECRET`, `LITELLM_*`, `GH_*`, `GITHUB_TOKEN`) from tool commands, keeps network on, and moves the tool caches into `/tmp`. `gh` in the sandbox authenticates per command with `GH_TOKEN_FILE=/agent-secrets/github/review`. Codex's Linux sandbox (bubblewrap) needs user namespaces and a `/proc` mount, which Docker's default seccomp profile refuses. `images/omnigent-host/test/codex-profile.sh` checks the profile, and checks the sandbox when it can start (locally: `docker run --privileged -u 1000660000 -v "$PWD/images/omnigent-host/test:/t:ro" -v <dir with fake code, knowledge and review files>:/agent-secrets/github:ro agent-stack/omnigent-host:dev bash /t/codex-profile.sh`).
- Git: `/etc/gitconfig.d/agent` sets `safe.bareRepository = explicit`, so a bare repository committed inside a checkout is never discovered and its `diff.external`, pager or hooks never run (only an explicit `--git-dir` opens one). It also sets `core.fsmonitor = false` and `protocol.file.allow = user`. `images/omnigent-host/test/git-safety.sh` checks all three against a planted bare repository.
