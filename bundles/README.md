# bundles

Omnigent agent bundles. `images/omnigent-server/Dockerfile` copies this directory to `/agents/` in the server image, and the server image registers all five through `OMNIGENT_BUILTIN_AGENT_DIRS`, which Omnigent seeds after its packaged agents. `OMNIGENT_SEEDED_AGENTS` keeps only the Claude Code and Codex harnesses of the packaged agents, so the packaged `polly` and `debby` are not offered. Each gets the built-in agent id, so its runner pods carry `omnigent.ai/agent: <name>`, and h-cloud's `agent-github-tokens` policy mounts only that agent's GitHub tokens: `review` for security-review, `review` and `knowledge-ro` for the planner, `code`, `knowledge` and `forks` for polly, `code` and `knowledge` for the documenter, `hcloud` and `knowledge` for infra ([h-cloud contract for `infra`](#h-cloud-contract-for-infra)).

A bundle's `model` doesn't choose the model of a session started from the Omnigent UI: Omnigent (checked on 0.19.1) starts managed sessions on the harness `default_model` from `config/omnigent/config.yaml` (`anthropic-auto` or `openai-auto`), and a different model is selected in the session. The Hermes runner's session tool (`omnigent_run`) passes each bundle's model explicitly.

| Bundle | Contents |
| --- | --- |
| `polly/` | Orchestrator adapted from Omnigent's example. It writes only `.polly/registry.json`, `.polly/diffs/` and its own skills (denied outside them for the file and patch tools, best-effort for the shell), and runs no mutating git verbs or pushes. `config.yaml` holds its instructions and tools, `agents/claude_code` and `agents/codex` the workers, `skills/` the skills `cross-review`, `fanout` and `investigate`. A turn that ends while a dispatched worker is still running is a status turn; `result_contract` requires the ```json result block only once every launched worker's inbox entry has been read |
| `planner/` | Read-only planner. `config.yaml` holds its instructions, the `code_graph` and `result_check` (`agent_stack_policies.mcp`) MCP servers and its policies (no writes, no pushes, GitHub read-only, at most 3 critic dispatches, validated final result), `skills/` the skills `plan-architect`, `plan-decompose` and `plan-contract`. `agents/critic` is the separate read-only critic on `claude-sdk` with `anthropic-auto` and the skill `plan-critic`: it grades each draft and returns findings and the coverage map, and the planner revises. A planner session spans several turns: its result is the first turn-final response carrying a ```json block, which `result_contract` has validated; earlier turns are interim, a consumer never reads a block from a non-final segment, and a consumer timeout or an idle session without a result counts as `BLOCKED{environment}` |
| `security-review/` | Read-only security reviewer on `codex-native` with `openai/gpt-astra`. `config.yaml` holds its instructions, the `result_check` (`agent_stack_policies.mcp`) MCP server and its policies (the planner's read-only set plus Codex's `apply_patch` and `spawn_agent` denied, a best-effort `process_secrets.no_process_secrets` gate (denies `/proc`, the Codex home and environment dumps) and `secret_files.no_secret_reads` gate that denies shell mentions of `/agent-secrets` other than `GH_TOKEN_FILE=/agent-secrets/github/review gh …` and the `gh` commands that print or hand out the token, validated security result), `skills/` the skill `security-audit`. Sessions need `terminal_launch_args: ["--profile", "security-review"]`, which selects the runner image's Codex profile (Codex's own bubblewrap sandbox off, `sandbox_mode = "danger-full-access"`; read-only is enforced by the policies and the read-only review token) `images/omnigent-host/codex/security-review.config.toml` |
| `documenter/` | Docs-only documenter on `claude-sdk` with `anthropic-auto`. `config.yaml` holds its instructions, the `result_check` (`agent_stack_policies.mcp`) MCP server and its policies (file-tool writes limited to docs paths with the forbidden paths still denied, shell writes outside them denied best-effort, commits limited to doc paths by the `docs_vcs` allowlist (a guardrail; the runner's post-run check blocks the card when the PR changes anything else), pushes without force, no merges, no Linear, validated documenter result), `skills/` the skills `docs-delta` and `docs-audit` |
| `infra/` | Autonomous h-cloud upgrader on `claude-sdk` with `anthropic-auto`, started through the Hermes runner lane (`hermes/agent_stack_hermes/runspec.py`, up to 6 h). It works the open Renovate PRs on `lkshrk/h-cloud` with the skill `upgrade-h-cloud` (ported from the owner's Hermes skill), pushes fixes to the PR's `renovate/*` branch, merges with the `land_renovate_pr` tool, health-gates each merge on the live cluster and returns an `infra` result (`merged`, `skipped`, `closed`, `failed` with RCA, `vault.commit`) that Hermes reports. `config.yaml` holds its instructions, the `result_check` and `renovate_land` (`agent_stack_policies.renovate_land --repo lkshrk/h-cloud`) MCP servers and its policies: `path_guard` with writes limited to `kubernetes/apps/<ns>/<app>/…`, the vault and `/tmp`, and `write_deny` on the protected paths (`agent_stack_policies.infra_paths.PROTECTED_PATHS`) that stay readable; `infra_vcs` (pushes only `git push origin HEAD:renovate/<branch>`, no remote changes, gh reads plus `gh pr comment` and `gh pr close`, which like gh GETs can target any repository the token reaches); `infra_cluster` (kubectl, flux and helm read verbs, plus `flux reconcile` without `--force` or `--reset`); `no_secret_reads` on `/agent-secrets`; the server `no_merge` still denies every shell, gh, API and GraphQL merge; 1500 tool calls per session; validated infra result. Before a push the agent runs `python3 -I -m agent_stack_policies.manifests_cli <base> <head>`, the post-run check's path and manifest rules on its local commits. `land_renovate_pr(number)` reads the token from `HCLOUD_TOKEN_FILE` (default `/agent-secrets/github/hcloud`) and squash-merges, as h-cloud merges Renovate PRs, only an open PR by `renovate-master[bot]` from a `renovate/*` branch of `lkshrk/h-cloud` into `main` that GitHub reports mergeable, whose check runs (success, neutral or skipped) and statuses on the head are green, whose required checks (`--require-check`: `Flate - Success` and `Verify SOPS Files Are Encrypted`) each ran and succeeded, and whose head branch history reaches its creation with every push by anyone else limited to app paths and passing the manifest checker; it merges with `sha` set to that head. The pod needs h-cloud's `hcloud` and `knowledge` tokens (`gitKey: hcloud`) and the `omnigent-infra` service account token projected at `/var/run/secrets/kubernetes.io/serviceaccount` (or a `KUBECONFIG`), both from h-cloud. h-cloud must also bound that service account with a ValidatingAdmissionPolicy that lets it patch Flux Kustomizations, HelmReleases and sources only in `metadata.annotations["reconcile.fluxcd.io/requestedAt"]`: `infra_cluster` is a guardrail and the RBAC `patch` verb alone would allow any patch. The image carries `flate` (the version h-cloud's `.mise.toml` pins) and `crane` for anonymous registry reads |

The Hermes session tool `omnigent_run` validates each bundle's result, runs the post-run check (`policies/README.md`, Post-run check) and stores the result's `gaps` and `doc_gaps` in the card metadata; linear-bridge lists them in its evidence comment on the Linear issue. Workers never create sub-issues.

One `omnigent_run` call has a wall budget of 2700 s (`CALL_SECONDS`, monotonic clock). It follows the session for the first 2100 s in slices of 300 s and keeps the last 600 s (`POST_RUN_RESERVE_SECONDS`) for the post-run check. A call reconciles the session snapshot before it first follows the stream, so a session that has already ended is judged at once. Each slice rereads the card, heartbeats it (renewing the 900 s Kanban claim) and reconciles the session snapshot, so stall detection (no session or child update for 2700 s), the bundle's runtime cap and outage handling work as before. Every SSE line, keepalive comments included, hands control back to the follower, so a quiet stream can't hold a slice past its deadline or starve the heartbeat. No slice starts with less than 120 s of the follow window left. A session that ends after the follow window is judged by the next call, and the post-run check itself may take 480 s (`POST_RUN_SECONDS`; each GitHub request's timeout is the time left, and paginated reads stop at the cap): a slower one blocks the card as `BLOCKED{environment}` (transient) instead of reporting a violation. The call returns early when the card is completed or blocked, or when the run no longer holds the claim; at the end of the window it returns `call_again: true` and the profile's small model calls it again, so a 6 h sweep takes about ten calls. A failed slice is retried after 15 s; three failures in a row end the call with the error and `call_again: false`, keeping the session id. Hermes's own tool deadline (420 s by default) would cut such a call, so the `omnigent-runner` profile sets `timeouts.tools.sequential_call` and `concurrent_batch` to 3600 s. If Hermes still abandons a call and the model starts another, both run under the same Kanban run: `kanban_complete` and `kanban_block` only change a card that is still open in that run, so only the first verdict is written and the other call returns without one. The SOUL tells the model that the result decides the card. When the model stops anyway, Hermes's Kanban stop nudge asks it (at most twice) for `kanban_complete` or `kanban_block`; the lane's `pre_tool_call` hook denies both and answers "Call omnigent_run now.", so the nudge puts the model back in the loop.

## Starting an infra sweep

Ask Hermes in Signal to "upgrade h-cloud" (or "run the Renovate sweep"; extra text, such as "skip cilium", goes to the agent as its task). The default profile's `upgrade-h-cloud` skill (`config/hermes/profiles/default/skills/`) runs `runner-start infra '<request>'` (`hermes/agent_stack_hermes/start.py`), which creates one `omnigent-runner` card with `agent-stack-link: null` and `agent-stack-run: {"bundle":"infra","repo":"lkshrk/h-cloud","ref":"main","input":"<request or the default task>"}`. It refuses while an infra card is not done or archived, blocked ones included: archive a blocked card (`hermes kanban archive <id>`) to start a new sweep. Hermes itself never touches h-cloud.

When a runner card without a Linear link completes or blocks, linear-bridge sends the owner one Signal message (`cmd/README.md`, linear-bridge): for infra the merged PRs, the agent's own pushes from `post_run.landed`, the skipped PRs with their reasons, closed and failed PRs (with RCA), post-run notes and the vault commit; for a blocked card its `BLOCKED` reason, marked 🔴 for a post-run check violation. Other bundles get a one-line status with the PR link.

## h-cloud contract for `infra`

The infra bundle needs these values from h-cloud (rollout step 4) and from the Hermes runner's environment. They are the contract; change both sides together.

Sandbox pod (`omnigent.ai/agent: infra`):

| What | Value |
| --- | --- |
| Kyverno `agent-github-tokens` token keys | `infra → [hcloud, knowledge]` |
| Kyverno `gitKey` | `hcloud`, so the host gets `GH_TOKEN_FILE=/agent-secrets/github/hcloud` and `GIT_TOKEN` from the `hcloud` key, and `KNOWLEDGE_TOKEN_FILE=/agent-secrets/github/knowledge` |
| `land_renovate_pr` token | `HCLOUD_TOKEN_FILE`, default `/agent-secrets/github/hcloud`; no env needed when the key is mounted there |
| `hcloud` token | octo-sts trust policy `agent-stack-infra-hcloud` (`TOKENS += hcloud=lkshrk@agent-stack-infra-hcloud`): `lkshrk/h-cloud` contents write, pull_requests write, issues write, workflows write, actions read, checks read, statuses read (as merged in `lkshrk/.github`). `workflows: write` stays: merging a Renovate PR that touches `.github/workflows` with an App token needs it |
| Cluster identity | Kyverno sets `serviceAccountName: omnigent-infra` and projects its token (3600 s), `kube-root-ca.crt` and the namespace at `/var/run/secrets/kubernetes.io/serviceaccount` in the `host` container, so `kubectl` and `flux` use in-cluster config; or a `KUBECONFIG` |
| `omnigent-infra` RBAC | get/list/watch on everything except Secrets; `patch` on Flux Kustomizations, HelmReleases and sources |
| Admission | a ValidatingAdmissionPolicy that lets `system:serviceaccount:omnigent-sandboxes:omnigent-infra` patch those Flux objects only in `metadata.annotations["reconcile.fluxcd.io/requestedAt"]`. `infra_cluster` is a guardrail; the RBAC `patch` verb alone allows any patch |

Hermes runner (`omnigent-runner` profile):

| Variable | Value |
| --- | --- |
| `GITHUB_RO_TOKEN_FILES` | `routivo=/var/run/agent/github/review,lkshrk=/var/run/agent/github/hcloud-ro` |
| `hcloud-ro` token | trust policy `agent-stack-runner-ro` (`TOKENS += hcloud-ro=lkshrk@agent-stack-runner-ro`): `lkshrk/h-cloud` contents, pull_requests, metadata and actions read (`actions: read` for the monthly-tag proof, `actions/workflows/tag.yaml/runs`); the policy comes from `lkshrk/.github` PR #16, not merged yet |
| `GITHUB_AGENT_ACTORS` | `h-cloud-npa[bot]`, the octo-sts GitHub App (id 5184450) whose installation tokens the agents push and merge with |
| `GITHUB_TRUSTED_ACTORS` | `renovate-master[bot],lkshrk`: pushes to a `renovate/` branch by these are not content-checked |
| `GITHUB_TRUSTED_MAIN_ACTORS` | `h-cloud-workflow[bot]`: workflow bots that push `main` themselves (image updates, model refreshes). Every other move of `main` during an infra run, an unattributed one included, must be a Renovate merge by an agent |

`land_renovate_pr` trusts only `renovate-master[bot]` on the head branch, which is stricter than the post-run check: an owner push to a `renovate/` branch is content-checked by the tool, so a PR the owner fixed outside the app paths is refused there and stays for the owner.
