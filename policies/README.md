# policies

Policies for other workloads: PR-Agent fetches its files from this repository at runtime, and the Omnigent package is baked into the Omnigent images.

| Path | Consumer |
| --- | --- |
| `pr-agent/pr-agent.toml`, `pr-agent/review.md` | The PR-Agent init container in h-cloud (`kubernetes/apps/ai/pr-agent`) fetches both from `main` at pod start and merges `review.md` into `extra_instructions`. Repository-local overrides remain possible |
| `omnigent/` | Omnigent policy package baked into the server and runner images |

## Guardrails, not the boundary

The shell gates are guardrails. They catch honest mistakes and tell the agent what to run instead; a determined or prompt-injected agent is expected to get past them.

Today:

- Runner pods get their GitHub token per agent from h-cloud's Kyverno policy `agent-github-tokens`, keyed on the pod label `omnigent.ai/agent`: Polly gets the `code`, `knowledge` and `forks` tokens, the documenter `code` and `knowledge`, the planner `review` and `knowledge-ro`, security-review only the read-only `review` token, infra the `hcloud` and `knowledge` tokens, every other pod none. The `code` token can push and merge, and main is not protected, so nothing outside these gates stops a Polly or documenter session from pushing or merging to main. The owner accepts that risk.
- The Hermes runner's post-run check (below) detects a push or merge outside the agent's branch, and a documenter change outside doc paths, after the session ends and blocks the card. It doesn't revert anything.
- The owner reviews the PRs, and git history keeps every change revertible. `infra` is the exception: it merges Renovate PRs on h-cloud itself, so its sandbox gates (`infra_vcs`, `path_guard` with `write_deny`, the `land_renovate_pr` checks) are guardrails in front of the post-run check, which is the enforcement.

Planned, not built yet:

- read-only shell startup files in runner pods (Task 11c);
- launch configs moved out of the writable HOME (Task 11d).

Parser gaps are tracked in the shell-gate follow-up issue (XXX-427).

## Post-run check

The Hermes `omnigent-runner` lane (`hermes/agent_stack_hermes/runner.py` and `postrun.py`) records the repository's branch and tag refs on the card before it creates a session, and compares them with GitHub once the session ends. A violation blocks the card as `BLOCKED{permission}` with `post-run check: …`; nothing is reverted, the owner decides. How long one `omnigent_run` call follows a session is in `bundles/README.md`.

- Protected branches are the run spec's ref and the PR's base and default branch, or without a PR the default branch. A move of a protected branch passes only when GitHub's repository activity explains it: every entry has an actor, none of them is in `GITHUB_AGENT_ACTORS`, and the entries chain from the recorded SHA to the current one. Otherwise it is `ref moved by agent` or `ref moved (unattributed)`. With `GITHUB_AGENT_ACTORS` unset every protected move is a violation.
- A moved tag is always a violation, a deleted one unattributed. A new tag passes when its release author is not an agent; without a release it is unattributed. `infra` runs have two more ways: the tag ref's activity actors (chained from creation to the ref's SHA, which for an annotated tag is the tag object, not the commit), and for h-cloud's monthly tags (name `YYYY.M.N` in ASCII digits with a month of 1 to 12, created by `.github/workflows/tag.yaml` with `git.createRef`, no release, no activity entry) a successful, completed `schedule` or `workflow_dispatch` run of `tag.yaml` from the run's repository (`GET /repos/{repo}/actions/workflows/tag.yaml/runs?head_sha=<commit>`) on the default branch whose head SHA is the tagged commit and which finished inside the run window. The tag object's tagger name plays no part.
- The PR's head must be in the run's repository and not a protected branch, and its base must be in the repository. The documenter's PR may change only doc paths.
- `infra` checks every PR in its result (`merged`, `skipped`, `closed`, `failed`; at most 100, more is a violation): each must be on the run's repository and passes the PR checks above. An agent may move the default branch only through `pr_merge` activity (at most 50 agent merges per run) whose new SHA belongs to exactly one PR (`GET /repos/{repo}/commits/{sha}/pulls`, asked again once after 5 s when it lists none) that is merged with that SHA as merge commit, is based on the default branch with base and head in the repository, has a `renovate/` head, is authored by `renovate-master[bot]` and was merged by a login in `GITHUB_AGENT_ACTORS`, with the activity chain intact. Any other agent move (push, force push, merge queue, a non-Renovate PR) and any agent move of another protected branch stays a violation. For `infra` this is deny by default: every move of the default branch whose actor is not in `GITHUB_TRUSTED_ACTORS` or `GITHUB_TRUSTED_MAIN_ACTORS`, an agent login or an empty actor included, must pass the same Renovate-merge rule, so an agent login missing from `GITHUB_AGENT_ACTORS` is still caught (its merge then fails the `merged_by` check). Other bundles keep the plain rule: an agent move of a protected branch is a violation.
- The agent may push fixes to the `renovate/` branch before merging. The check reads that branch's activity from the PR's head SHA back to the branch's creation; the entries must start at a creation and chain push to push up to the head SHA. A branch recreated under the same name starts a new history; a history that doesn't reach a creation within the page cap, or has a gap, is a violation. Only pushes by `GITHUB_TRUSTED_ACTORS` (default `renovate-master[bot]`; an agent login is never trusted) are trusted. Every other push, and every push without an actor, is untrusted (at most 20 per PR): what it introduced (`GET /repos/{repo}/compare/{before}...{after}`, or from the PR's base SHA for a branch creation or force push) is checked file by file. This keys on the authenticated pusher that GitHub records, not on commit authorship, which a pusher can set to anything.
- An untrusted push may change only files inside an app directory, `kubernetes/apps/<namespace>/<app>/…` (`agent_path_allowed`; both sides of a rename), and never the paths in `PROTECTED_PATHS`: `kubernetes/apps/security/**`, `kubernetes/apps/omnigent-sandboxes/**`, `kubernetes/apps/ai/hermes/**`, `kubernetes/apps/ai/contribution-approver/**`, `kubernetes/apps/actions-runner-system/**`, `kubernetes/apps/flux-system/**`, `kubernetes/apps/ai/omnigent/**`, `kubernetes/apps/system-upgrade/**`, `kubernetes/apps/kube-system/**`, `kubernetes/flux/**`, `.github/**`, `talos/**`, `**/*.sops.yaml` and any `ks.yaml` (Flux Kustomization wiring). A push may change at most 50 files, and a branch creation or force push must be ahead of the PR base (compare status `ahead` or `diverged`), so a base that already contains the head is a violation. Every changed file is then read at both ends of the push (`GET /repos/{repo}/contents/{path}?ref=`, the old path for a rename; 404 is absent, a file over 1 MB or a non-file is a violation) and checked by the manifest checker below. A violation names the PR, the push (`before..after`) and the file. A push that merges the default branch into the `renovate/` branch (GitHub's update-branch) compares everything it brought in, so it over-reports and fails closed.
- The manifest checker (`policies/omnigent/agent_stack_policies/manifests.py`, `check_change(path, before, after, previous)`) parses instead of scanning diff text, so flow or JSON YAML, quoting, escapes and odd spacing don't matter. Only `.yaml`, `.yml`, `.json` and `.md` files may change (`.md` is not parsed). A file with a CR, NEL, LS or PS character, invalid UTF-8, a YAML tag or directive (`!`, `%TAG`), a merge key (`<<`), a duplicate key, nesting deeper than 64 levels (also through aliases), aliases that expand past 100,000 nodes, or a parse error is a violation, and every document must be a mapping. A file renamed from another directory counts as entirely new. Documents are matched by (apiVersion, kind, namespace, name); an added or changed document must be one of `ALLOWED_KINDS` (Deployment, StatefulSet, DaemonSet, Job, CronJob, Service, ConfigMap, PersistentVolumeClaim, Ingress, HTTPRoute, PodDisruptionBudget, HorizontalPodAutoscaler, ServiceMonitor, PodMonitor, PrometheusRule, HelmRelease and the kustomize Kustomization, each at its listed apiVersion), so RBAC, Flux Kustomizations and sources, and admission policies can't be added or edited; a non-allowlisted document may stay only if it is unchanged, and neither it nor a kustomization may be removed.
- Field rules, searched everywhere in an allowlisted document including pod templates and HelmRelease values, and keyed by their place (list entries by `name`, `mountPath`, `containerPort` or `key`), so moving or copying a value to another container counts as new while reordering or inserting entries doesn't: no new or changed `POD_FIELDS` (service account fields, `hostPath`, `hostNetwork`, `hostPID`, `hostIPC`, `hostPort`, `hostUsers`, `hostAliases`, `privileged`, `allowPrivilegeEscalation`, `runAsNonRoot`, `procMount`, `seccompProfile`, `appArmorProfile`, `shareProcessNamespace`, `nodeName`, `sysctls`, `priorityClassName`) or added capabilities; `runAsUser`, `runAsGroup` and `fsGroup` must be plain integers of at least 1; and no new Secret or credential reference: any key containing `secret` (`secretKeyRef`, `secretRef`, `secretName`, `bearerTokenSecret`, …) and `SECRET_SOURCES` (`basicAuth`, `authorization`, `oauth2`, `csi`, `flexVolume`, `nfs`, `iscsi`, projected `serviceAccountToken`, `imagePullSecrets`). A new document may not set `metadata.namespace`. A HelmRelease keeps `HELMRELEASE_FIXED_FIELDS` (`chart`, `chartRef`, `postRenderers`, `serviceAccountName`, `targetNamespace`, `storageNamespace`, `kubeConfig`, `valuesFrom`) and every values key matching `SENSITIVE_VALUES` (rbac, serviceAccount, clusterRole, extraObjects, extraManifests, extraDeploy, extraResources, additionalResources, rawResources, hostNetwork, hostPath, privileged, secret) unchanged, so a new HelmRelease can't be added. A ConfigMap's `data` and `binaryData` entries that parse as a YAML mapping (such as the values a HelmRelease reads through `valuesFrom`) follow the same values and field rules, and so do top-level lists. An entry that isn't YAML at all is plain text; YAML the checker can't read (alias errors, deep alias chains, tags, duplicate or merge keys, several documents) is a violation. Timestamps are read as plain strings everywhere. Image repositories are fixed: an `image` string anywhere in an allowlisted document (pod specs, HelmRelease values, YAML ConfigMap values) may change only its tag or digest, the part after the last `:` of its last path segment or after `@`, and a `repository` or `registry` string value (any depth, any case) may not change; an image at a new location, such as an added container, counts as a change. A kustomize `images[]` entry keeps its `name` and `newName` (an added entry may set only `newTag` or `digest`, and none may be removed). A PersistentVolumeClaim keeps `volumeName`, `dataSource`, `dataSourceRef` and `storageClassName`. A kustomize `kustomization.yaml` may only change `images` and add local resources in its own directory (`./x.yaml`; no `..`, subdirectories or URLs); `namespace`, `patches`, `components`, generators and every other field stay as they are, and no resource may be removed. Plain values files and other non-manifest YAML fail closed.
- Residual risk: Flux applies app manifests with the kustomize-controller's rights, so the content allowlist is the control. Within it an agent can still list an existing, unchanged file of the directory as a resource, change Ingress and HTTPRoute annotations and `parentRefs`, reuse the Secret and other same-namespace references a document already has, and change a container's `command` or `args` under its existing service account.
- A completed `infra` card's metadata carries `post_run: {status, landed, notes}`: `landed` lists each PR the agent merged (URL, merge commit and each untrusted push with its before and after SHA and files), `notes` the mismatches with the result (a landed PR missing from both `merged[]` and `failed[]`, a `merged[]` PR that GitHub shows unmerged). Notes don't block the card. Other bundles keep `post_run: "ok"`.

The runner reads GitHub with read-only tokens from these environment variables:

| Variable | Meaning |
| --- | --- |
| `GITHUB_RO_TOKEN_FILES` | Comma-separated `owner=path` pairs, e.g. `routivo=/var/run/agent/github/review,lkshrk=/var/run/agent/github/hcloud-ro`. The token file is chosen by the repository owner, case-insensitively |
| `GITHUB_RO_TOKEN_FILE` | Token file for owners not listed in `GITHUB_RO_TOKEN_FILES` |
| `GITHUB_AGENT_ACTORS` | Comma-separated GitHub logins of the agents' Apps |
| `GITHUB_TRUSTED_ACTORS` | Comma-separated logins whose pushes to a `renovate/` branch an `infra` run trusts, and whose moves of the default branch it accepts; default `renovate-master[bot]` |
| `GITHUB_TRUSTED_MAIN_ACTORS` | Comma-separated logins (workflow bots) whose moves of the default branch an `infra` run accepts; unset means none |

The values h-cloud and the runner set for `infra` are listed in `bundles/README.md`, [h-cloud contract for `infra`](../bundles/README.md#h-cloud-contract-for-infra).

At least one of the two token variables must be set, and a malformed `GITHUB_RO_TOKEN_FILES` counts as not configured; the reason names the entry by its position, never its text. A run whose repository owner has no token file blocks as `BLOCKED{environment}` before a session is created. Token files are read on every request and their contents never appear in a reason or log.

## Omnigent shell gates

`no_merge`, `no_nested_agents`, `path_guard`, `docs_vcs`, `read_only_shell`, `git_verbs` and `no_secret_reads` share one parser and command resolver (`agent_stack_policies/_shell.py`). It walks `sh -c`/`bash -c` (and the other shells), `eval`, the `$(…)` and backtick bodies bash runs (none inside single quotes, `$'…'`, comments or quoted heredocs such as `<<'EOF'` or `<<'EO'F` (a delimiter quoted with `$'…'` or `$"…"` is denied), and no escaped backtick; a `#` starts a comment only at the start of a word and outside `${…}`, and `$'` is text inside an unquoted heredoc), process substitutions and here-strings into a shell, and strips leading keywords, `VAR=` assignments and the wrappers `env` (including `-a`/`--argv0`, and `-S`, whose words `env` reads as its own arguments again), `command`, `builtin`, `exec`, `nohup`, `setsid`, `ionice`, `nice`, `timeout`, `flock` (and `flock -c`), `stdbuf`, `time`, `xargs`, `find -exec`/`-execdir`/`-ok`/`-okdir` (every run, each ending at a quoted or escaped `;` or at `{} +`), `sudo`, `doas`, `su -c`/`--session-command` (and `su -s <program>`), `script -c`, `watch` (including `-q`/`--equexit`), `parallel`, `npx`/`bunx`/`pnpx`, `pnpm dlx`/`pnpm exec`, `yarn dlx`/`yarn exec`, `npm exec`/`npm x`, `bun x`, `uv run`, `uv tool run`/`uvx` and `mise exec`/`mise x` (`--` or `-c`). A unique abbreviation of an installed wrapper's long option (`env --arg`, `watch --equ`) is read as that option, as getopt_long reads it, and every gate denies an unknown or ambiguous one (`ionice --cl`). Only an unquoted `;`, `&`, `|` or newline ends a statement; a quoted or escaped one (`\;`, `';'`) is an argument, as in bash. Every gate denies a command longer than 16,384 characters, a command with more than 160 statements, `(…)` groups and nested commands (each `find` run, `-c` body and `$(…)` body counts, also when a body only splits roughly), and a command with more than 1,024 words across those units. The reason names the limit that was hit and suggests splitting the command, or putting a long script in a file under the workspace and running that; a large file is written with the Write tool, which these limits don't apply to. So a command with a heredoc that takes it over 16,384 characters is denied, by design. Within the limits, the slowest full policy call took about 34 ms on the development machine, so about 50 ms on a GitHub runner. The suite doesn't assert that number. It checks that cost grows linearly: with the limits lifted, eight times the input must take less than twelve times the CPU time, in every bundle's policy stack. It also checks a loose ceiling of 150 ms per call. Parsing costs time per character, which is why the length limit is checked first, before any parsing. Every gate also denies a `find` with an `-exec`, `-execdir`, `-ok` or `-okdir` word inside another run's command, because it can't tell which runs find starts. `no_nested_agents` also denies a script piped into a shell (`| sh`, `bash -s`, `bash < file`) and commands piped into `parallel`, and exempts only each CLI's own help and version flags (`codex -V`, `claude`/`omp`/`opencode -v`).

`read_only_shell` is an allowlist for report-only agents: read commands (`rg`, `cat`, `head`, `sed -n` line ranges, git read verbs and similar, `gh` reads with `extra_commands: [gh]`), no `VAR=` or `env VAR=` assignments, no token containing `>` other than `>`/`>>` into `/dev/null`, no `find -delete`, `sort -o`/`--compress-program` or `rg --pre`, and `exact_commands` allowed verbatim. The planner, its critic and Polly's Codex worker run under it. `git_verbs` limits git to read verbs plus `extra_verbs`; Polly gets `fetch` and `worktree`. With `allow_only`, `path_guard` denies writes outside the scope for the file and patch tools and, best-effort, for the shell: redirect targets (`>`, `>>`, `<>`, `&>`, `&>>`, `>|`, `>&`), `tee` files, `sed -i`/`--in-place` files, `cp`/`mv`/`install`/`ln`/`rsync` destinations (including `-t DIR`, `-tDIR`, bundled `-rt DIR` and `--target-directory`), `mv` sources, `touch`/`rm`/`rmdir`/`truncate`/`mkdir`/`chmod`/`chown`/`chgrp` targets and `dd of=` outside the scope are denied. `/tmp`, `/tmp/…` and `/dev/null` are always allowed; any other absolute, `~` or `..` target, and any target that needs `$`, backtick or brace (`{a,b}`, `{1..3}`) expansion, is denied. Quoted operator words (`'<'`, `';'`) are read both as literals and as operators, because `eval`, `watch` and `parallel` join them back into a shell string. `exempt` only lifts a `deny` match and never widens `allow_only`, and an unparseable shell command is denied whenever `deny` or `allow_only` is set. A relative path matches `allow_only`, and `docs_vcs`'s `git add` `allow_paths`, from the checkout root (`docs/**` covers `docs/a.md`, not `backend/docs/a.py`; a pattern starting with `**/` still matches at any depth), while `deny` matches at any depth. The policy event doesn't carry the session's cwd yet, so an absolute file-tool path (Write and Edit send them) or `git add` path is still matched at any depth, and `/etc/docs/x.md` passes `docs/**`; shell write targets that are absolute are denied outside `/tmp` and `/dev/null`. A worker may configure `startup_files` and `startup_home` to deny a write target or shell token that names one of those files exactly: `~`, `~<basename of startup_home>`, `$HOME`, `${HOME}`, `"$HOME"` and any `${HOME…}` parameter form are replaced with the HOME path, and the result is normalised before the comparison. The shell's quotes are gone from a token by then, so a `${HOME…}` form is read once with each later `}` as its closing brace, and a token that names a startup file with more than 64 such readings is denied. Root-relative dotfiles remain repository files because the event carries no cwd. Not covered: a relative path after `cd`, a shell init file selected by `BASH_ENV` or `bash --rcfile`, files that other commands write (`sort -o`, `git diff --output`, compilers, a build or test command), an expansion in another operand that produces the target (`cp {/tmp/a,src/a}`), abbreviated GNU long options (`--target=`, `sed --in-pl`) and globs such as `.?` that match `..`. Process substitution bodies (`<(…)`, `>(…)`) are walked as statements by every gate. `read_only_shell` takes bare command names only, allows no wrapper except `command` and `find -exec` (no shell through `find`), and allows only the stderr redirects `2>/dev/null` and `2>&1`. It also denies variable-assigning builtins (`printf -v`, `read`, `mapfile`, `declare`, `export`, `let`, `getopts` and the like), `test -v`, and arithmetic, subscript, substring and indirect expansions (`$((…))`, `((…))`, `$[…]`, `${x:…}`, `${a[…]}`, `${!x}`). `git_verbs` denies any variable assignment in a command that runs git, and `no_merge` denies a variable in a push or merge. A `${…}` with `:`, `[`, `@` or `!` after the name (substrings, subscripts, `@P`/`@E`/`@Q`/`@A` transformations, indirection) is opaque: `read_only_shell` and `git_verbs` deny it outright, and `no_merge`, `no_nested_agents` and `docs_vcs` deny it when the command mentions git, gh or an agent CLI or names an opaque command, and always for the decoding `@P`/`@E`. Every gate that walks `-c` bodies denies positional arguments after the body. `git_verbs` denies git run through `xargs` or `parallel`. `no_merge` denies `parallel`, which no image installs ("parallel is not available; run commands directly"), and the unwrapped launchers `capsh`, `runuser`, `sg`, `setpriv`, `unshare`, `nsenter`, `chroot`, `taskset`, `prlimit`, `setarch`, `linux32`, `linux64`, `x86_64`, `i386`, `uname26`, `xvfb-run`, `bwrap`, `start-stop-daemon`, `chrt`, `strace`, `ltrace`, `gdb` and `valgrind`, and the dynamic loader names `ld.so` and `ld-linux*.so*`, each with "<name> is not allowed; run commands directly". A `command` lookup (`-v`/`-V`, with optional `-p`, before its first operand) runs no launcher and is allowed. It permits `xargs` only for these literal read/format programs: `rg`, `grep`/`egrep`/`fgrep`, `wc`, `cat`, `head`, `tail`, `ls`, `stat`, `file`, `echo`, `printf`, `basename`, `dirname`, `realpath`, `readlink`, `cut`, `tr`, `jq`, `sha256sum`, `md5sum`, `du`, `test` and `true`. It denies every other program, a quoted, escaped or templated command word, a command word containing a replacement string that xargs's own options set (`-I R`, `-iR`, `--replace=R`, read only up to the command word), and a command loaded from arguments or a file. Run gh and git directly. `no_merge` also denies `gh pr merge` and the `gh api` merge routes (`pulls/<n>/merge`, `/merges`, case-insensitive). It treats a `gh api` request to the GraphQL endpoint in any spelling gh routes there (`graphql`, `/graphql`, a full or GHES `…/api/graphql` URL) as GraphQL, and denies one that contains a merge mutation (`mergePullRequest`, `mergeBranch`, `enablePullRequestAutoMerge`, `enqueuePullRequest`). A GraphQL request may use literal fields only: each `-f`/`-F`/`--field`/`--raw-field` value, including one in a pflag short cluster such as `-iFkey=value`, needs a `key=` whose key, after the shell's dequoting, has no `$`, backtick, glob or brace, and no extra argument such as `"$@"` may follow the endpoint. Its `query` value must not expand: a `$`, `$(…)` or backtick outside single quotes, or `$'…'` quoting anywhere in the command, is denied. A query from a file or stdin (`query=@…`, `--input`) is denied too, including `-f query=@…`, which gh sends as a literal string. A script or interpreter that sends the request (`bash /tmp/m.sh`, `python3 -c`) still gets past these checks, and today the `code` token can merge and main is not protected; the runner's post-run check detects such a merge afterwards and blocks the card, it doesn't undo it. `gh alias` and `gh extension`/`extensions`/`ext` are denied except `list`/`ls`, because they can define a command that merges. So is any gh command while `GH_CONFIG_DIR` or `XDG_CONFIG_HOME` is assigned in the same command, because both can load aliases from another config. It also denies force-pushes, tag and other non-branch ref pushes (`--tags`, `--follow-tags`, `--all`/`--branches`, `--mirror`), pushes to a protected branch, and any push without an explicit destination it can check (no refspec, or a bare `HEAD` or `@`); the remedy is `git push origin HEAD:<branch>`. It finds `push` after git's global options, using the git 2.47 and 2.56 table (`-C`, `-c`, `--config-env`, `--git-dir`, `--work-tree`, `--namespace`, `--attr-source` and `--shallow-file` take a separate value); any other long global option without `=` is denied when the resolver finds the git command, or when an unresolved `git` word is followed by `push`, `merge` or `config`, so a newer value option can't shift the arguments. It reads push options as git does: short clusters (`-uo X`), unique long-option prefixes (`--force-w`, `--push-opt`) and the options that take a value (`-o`, `--push-option`, `--repo`, `--receive-pack`, `--exec`, `--recurse-submodules`); an ambiguous prefix is denied, and `--` or `--end-of-options` ends the options. It checks `-c`, `--config-env`, `GIT_CONFIG_*`, `GIT_CONFIG_PARAMETERS` and `git config <key> <value>` writes for config that can redirect a push or merge: `alias.*`, `push.*`, `url.*`, `include.*`, `includeIf.*`, `remote.pushDefault`, `remote.<name>.push`/`url`/`pushurl` and `branch.<name>.merge`/`remote`, plus pointing git at another config file (`GIT_CONFIG`, `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`).

The gates read tokens, not a running shell. A command named through a variable (`$G push`), an alias written into a config file git loads (a hand-edited `.git/config`, a `git config <key> <value> get|list` value-pattern write, `git config --rename-section`, or a `.gitconfig` under another `HOME` or `XDG_CONFIG_HOME`), a gh alias or extension loaded from config under another `HOME=` or `XDG_DATA_HOME=`, or through a `GH_CONFIG_DIR`/`XDG_CONFIG_HOME` value set by `read` or `printf -v` before `export`, a copied binary or a launcher outside the list above (`ssh`, `docker exec`) is not resolved, and neither is a relative path after `cd`. A startup-file guard that is configured for a worker matches exact paths only: globs, braces, dotglob settings, runtime-built names and a relative `.bashrc` after `cd ~` all pass it. Nothing else stops a startup-file write today; read-only startup files in the runner pod (Plan 2 Task 11c) are planned, not built.

The shell gates also don't see code that is decoded at runtime (`printf '%b' … | bash`, `$'\x67it'`, `source <(…)`) or put in a script file and run (`bash s.sh`, `make push`). Nothing in this package stops those; Guardrails, not the boundary lists what limits them today and what is planned.

`no_secret_reads` (security-review) denies shell words naming `/agent-secrets`, other than the `GH_TOKEN_FILE=… gh` form, and the gh commands that print the token. It does not see paths built inside an interpreter (`python3 -c`, `node -e`, `awk`), reached by filesystem search (`find / … -exec cat`, `grep -r . /`), named relative to `/` after `cd /`, or matched by a glob that isn't normalised first (`/tmp/../agent-secret?/…`), and nothing else limits those reads. What such a read reaches is limited by the pod: a security-review pod holds only the read-only `review` token, and no `code` or `knowledge` token.

## infra gates

`path_guard` takes `write_deny` next to `deny`: a `write_deny` path is denied as a file-tool, patch or shell write target, but a shell command may still name it, so the infra agent can read `kubernetes/flux/**` and run `scripts/flate-test.sh --path ./kubernetes/flux/cluster` while it can't edit them. The infra bundle lists `PROTECTED_PATHS` there and limits writes to `kubernetes/apps/*/*/**/*`, the vault and `/tmp` with `allow_only`; the shell side is best-effort, like every write scope above.

`infra_vcs` allows exactly `git push origin HEAD:renovate/<branch>` (branch words of letters, digits, `.`, `_` and `-`, no options, no global git options, no wrapper, no expansion), denies `git remote` changes, and allows gh only for `pr view|diff|checks|list|status|comment|close` (`close` without `--delete-branch`), `issue view|list|status`, `release view|list`, `run view|list|watch`, `repo view`, `search`, `status`, `auth status` without `--show-token` and read-only `gh api`. The server's `no_merge` still applies on top, so force, tag and protected-branch pushes and every merge path stay denied. gh reads, comments and closes are not limited to one repository; the token decides what they reach.

`infra_cluster` reads kubectl, flux and helm after the shell wrappers and allows only kubectl `get`, `describe`, `logs`, `events`, `wait`, `auth whoami|can-i`, `top`, `version`, `api-resources` and `explain`; flux `reconcile` (without `--force` or `--reset`), `get`, `logs`, `trace`, `tree`, `diff`, `stats`, `version` and `check`; helm `template`, `show`, `pull`, `search`, `history`, `status`, `get`, `list`, `version`, `repo add|update` and `dependency build`. An option it doesn't know before the verb is read as a flag, so its value becomes the verb and the command is denied.

`agent_stack_policies.infra_paths` holds `PROTECTED_PATHS` and `agent_path_allowed` for the sandbox; a Hermes test keeps them equal to the post-run check's copies. `python3 -m agent_stack_policies.manifests_cli <base> <head>` (or `--staged <base>`) runs those path rules, a 50-file cap, a regular-file mode check and `manifests.check_change` on the local diff, prints `ok` or one `violation:` line per finding, and exits 0 when clean, 1 on a violation and 2 on a usage or git error. `python3 -m agent_stack_policies.renovate_land --repo <owner/repo> [--require-check <name>]…` is the stdio MCP server behind `land_renovate_pr`; it reads its token from `HCLOUD_TOKEN_FILE` (default `/agent-secrets/github/hcloud`), requires each named check run on the head to have completed with `success`, and otherwise mirrors the post-run check's Renovate merge rule, and it never prints the token. Both are guardrails: the token in the pod can still merge or push through a script, and the post-run check catches that afterwards.
